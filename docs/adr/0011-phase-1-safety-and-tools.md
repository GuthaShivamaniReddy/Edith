# 11. Phase 1: safety gate, privacy grants, tools and routing

Status: accepted · 2026-11-12 · supersedes decision 1 of [0010](0010-phase-0-runtime-decisions.md)

## Decisions
1. **The gate is wired through two SDK hooks.** A `PreToolUse` hook with no matcher (every tool) calls `SafetyGate.pre_tool`, which allows, denies, or answers `ask`. An `ask` reaches `can_use_tool`, where `SafetyGate.confirm` shows the user the exact action and waits. If nobody answers, the action is refused (`safety.confirm_timeout_s`). `allowed_tools=[]`, so nothing is pre-approved, and `PostToolUse` records the outcome. Every decision, confirmation, grant and outcome goes to `<data_dir>/audit.jsonl`, with secrets masked.
2. **Built-in tools: only WebSearch, WebFetch and AskUserQuestion.** Claude Code's file, shell and edit tools stay off. EDITH's own tools are in-process SDK MCP servers (`edith/tools`), one server per group. Their tiers come only from `config/permissions.yaml`, never from the tool code. If a tool has no explicit tier, EDITH refuses to start.
3. **Privacy: default-deny access grants.** Tools that read the computer (files, clipboard, screen, system info) need a grant from the user even at tier 0. A grant can be "once" or "for this session". Grants are never written to disk. Clipboard and screen access can only be granted once. `files.blocked_roots` can never be granted. Paths are resolved, with `..` and symlinks followed, before the scope check. The file tools check scope again as a second line of defence.
4. **Data-flow rules per request.** Once local data has been read, every outbound tool (web search, fetch, open URL) asks, and the confirmation shows exactly what would be sent. Once untrusted content (web, files, clipboard) has been read, tier-1 actions are raised to "ask" as a prompt-injection defence.
5. **Router: rules only.** A Haiku classification call would add 0.5–2 s to every request. Keyword and length rules pick Haiku for short chat and Sonnet for anything that may need tools, live data or files. When the rules are unsure, they pick the stronger model. Deep research goes to Sonnet until Phase 6.
6. **Fast path.** Stop words, time and date, volume, mute and timers are matched with regular expressions and need no model call. Fast-path tool calls still go through the same gate and audit log, marked `via=fast_path`. If the policy would ask about one of them, the command goes to the model instead.
7. **Kill switch.** "stop" (fast path), Ctrl+C in the terminal, or `{"type":"stop"}` on the WebSocket ends the caller's event stream at once. It also refuses every pending confirmation and question, then interrupts the SDK client. A stopped request's SDK messages are drained before the next request starts.
8. **Budgets.** The orchestrator checks the daily cap before each model call. The brain estimates spend from streamed token counts using `PRICES` and interrupts the request when it passes `min(per_request_usd, daily budget left)`. The recorded cost always comes from the SDK.
9. **Sessions.** Each conversation has its own brain (SDK client), safety gate and grants. At most 8 brains stay alive, and the least-recently-used idle one is closed first.
10. **The API listens on loopback only, and checks the Origin header.** `server.host` accepts only loopback addresses. The WebSocket accepts only same-origin browser connections (or clients that send no Origin), so a web page on another site cannot drive EDITH through the user's browser.
11. **Evals run against a sandbox.** `edith eval` runs scenarios with a fake system adapter, a temporary data folder and a temporary file sandbox. Confirmations are answered by each scenario's script. Web search and the model are real, so an eval run costs money and is never part of `pytest`.
